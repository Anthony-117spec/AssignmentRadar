## 1. 一句话概括

**AssignmentRadar 是一个伪装成"你本人"的小程序，每隔两小时替你浏览一遍平台上的所有课程页面，
把看到的作业记在一本本地台账里；台账一有变化（新作业、改截止时间、临近截止），它就弹通知。**

它不碰你的密码、不替你提交任何东西、所有数据只存在你自己的电脑上。

## 2. 整体架构：一台雷达的四个舱室

整个程序是**一个 Python 进程**（可以理解为一个正在运行的应用），内部像轮船一样分成四个
互不干扰的舱室，各干各的活，同时运转：

```
┌─────────────────────────────────────────────────────────────┐
│                    AssignmentRadar 进程                      │
│                                                             │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐       │
│  │ ① 轮询舱      │  │ ② 传令舱      │  │ ③ 面板舱      │       │
│  │ Poller 线程   │  │ Notify 线程   │  │ Dashboard线程 │       │
│  │ 定时出海侦察   │  │ 排队发通知     │  │ 本地小网站     │       │
│  └──────┬───────┘  └──────▲───────┘  └──────────────┘       │
│         │                 │                                  │
│         ▼                 │                                  │
│  ┌─────────────────────────────┐  ┌──────────────────┐      │
│  │ ④ 台账舱（SQLite 数据库）     │  │ ⑤ 托盘图标        │      │
│  │ data/state.db 唯一事实源     │  │ 状态灯 + 右键菜单  │      │
│  └─────────────────────────────┘  └──────────────────┘      │
└─────────────────────────────────────────────────────────────┘
          ↕ 互联网（只访问 moodle.scnu.edu.cn）
```

"线程"可以理解成**同一条船上的多个水手**：程序启动后，四个水手同时开始干活——
一个负责定时出海侦察（轮询），一个负责把侦察结果写成通知送出去，一个负责在本地
开一个小网站给你看，还有一个管着数据库这本台账。他们互不等待，谁也不阻塞谁。

## 3. 它凭什么能看见作业：网页抓取原理

### 3.1 网页的本质

你在浏览器里看到的平台页面，本质上是一份**HTML 文本文件**——一种用尖括号写标记的
文档，就像这样：

```html
<li class="activity assign">          <!-- 一个"作业"条目开始 -->
  <a href="/mod/assign/view.php?id=123456">
    <span class="instancename">第二周作业</span>
  </a>
</li>
```

浏览器的工作是把这些标记**渲染**成你看到的漂亮页面；而 AssignmentRadar 做的事是
**不渲染、直接读原文**——程序里有一个叫 BeautifulSoup 的解析器，能像用筛子一样，
用"选择器"（一种描述位置的规则，比如"找出所有 class 里带 assign 的条目"）从几万字
的原文里精准捞出作业的名称和链接。

### 3.2 它不是"黑客"，只是"代你浏览"

程序访问平台的方式和你用浏览器访问**完全一样**：同样的网址、同样的请求方式、
同样带着你的登录凭证（cookie，见下一节）。区别只有一个：浏览器把页面画出来给你看，
而程序把页面里"作业"相关的条目抽出来记台账。

老师能看到的每一个作业，你的工具才能看到；老师没布置、或你没加入的课程，它一样看不到。

### 3.3 三种"找课程"的手段（层层兜底）

学期开始时，程序要回答"这学期你有哪些课"。它有三级手段，从最可靠到最通用：

1. **读"我的课程"侧边栏**（首选）：平台页面左侧那个课程列表是教务系统同步的、
   由服务器直接生成的，最准。程序在里面找"26-27上学期"这个分组，只取组内的课——
   这就是你"只要这 6 门课，其他都是噪音"需求的实现方式；
2. **调 Moodle 官方接口**（备用）：Moodle 平台自带一套给手机 App 用的官方数据接口，
   程序会请求它拿课程列表（缺点：会混进学校统一塞给所有人的培训课）；
3. **扫页面上的课程链接**（保底）：最笨但最通用的办法，把页面上所有指向课程页的
   链接都收集起来。

三级的实际效果：第一级成功就不会用后两级，所以你只会看到本学期那 7 门课。

## 4. 最难的一关：让程序保持登录

这是整个项目里技术上最麻烦的部分，值得单独讲。

### 4.1 cookie：临时门禁卡

网站怎么知道"这次请求是你本人发的"？靠 **cookie**——登录成功后，网站发给你浏览器
一小段暗号，之后每次访问都随身携带，网站验暗号放行。可以理解为**临时门禁卡**。

问题在于：**平台的门禁卡有效期极短，而且频繁更换**。实测中，把浏览器里的门禁卡
复制给程序，十几分钟后就作废了——因为网站每隔几分钟就发一张新卡、作废旧卡
（安全机制，叫"会话轮换"）。你自己的浏览器不掉线，是因为它每次都乖乖换用新卡；
而一个复制走静态卡片的程序，很快就对不上号了。

### 4.2 两层凭证：门禁卡 + 身份证

平台的登录是两层的：

- 上层是学校**统一身份认证**（sso.scnu.edu.cn，所有校园系统共用，登录一次管很久）；
- 下层是平台自己（moodle.scnu.edu.cn，靠上层发的临时票据维持）。

打个比方：**SSO 是你的校园身份证，平台的 cookie 是凭身份证办的临时门禁卡**。
门禁卡天天换没关系，随时能凭身份证再办一张。不过身份证也有"太久不用就作废"的规矩
（实测约一天不活动就会失效）——所以程序除了自动续期，还会定期"亮一下身份证"（保活），
别让它悄悄过期。

### 4.3 程序的三级防线

| 防线 | 做法 | 现状 |
|---|---|---|
| 第一级 | 直接用你复制的门禁卡 | 有效期内工作完美 |
| 第二级 | 拿你的"身份证"（SSO cookie）自动重走登录流程，重新办卡 | 登录链路已全自动（确认页自动确认、拿授权码、网关回调）；续期后以链路中网关派发的**整套 cookie** 重建会话并实测验证。但网关回调最后不认程序环境的登录结果（8 组对照实验定位为服务端行为）——**最后一公里未打通** |
| 保活 | 每轮成功轮询后顺带走一遍登录链路，给"身份证"续命（限频每小时） | 防止 SSO 会话因"一天不活动"悄悄过期；一旦发现 SSO 已失效，趁门禁卡还能用时提前弹预警 |
| 第三级 | 前两级都失效时，弹通知"请重新复制 cookie" | 30 秒手工操作，保底可用 |

程序还带了**会话体检**：每次访问都检查返回的是不是登录页，一旦发现被弹到游客状态，
立刻判定期过期并触发上述防线，绝不带着过期凭证空转。

> **补充结论（2026-10-08）**：把这条链路完整走通并逐步核对之后确认——网关确实下发了
> 全新的 `MoodleSession`，也就是说浏览器侧的会话是真实存在的；但网关始终没把入口票据
> 升级成登录态，`/my/` 依旧跳游客首页。**即：卡点在网关服务端，不在本工具的代码里。**
> 这一点决定了后面 4.4 的取舍：既然服务端不认，就不再在这条路上耗，改为直接借用浏览器
> 已经拿到的会话。

### 4.4 借用浏览器的会话：两条取会话路径

既然纯 HTTP 客户端复现不了浏览器的登录落地，那就**不再复现，直接借用浏览器已经拿到的会话**。
两条路径，首选第一条。

**路径一：`radar.bat import` —— 从浏览器本地存储读取会话（首选，但受新版 Chrome 限制）**

浏览器会把 cookie 加密后存在本地磁盘。旧版 Chromium 的加密密钥绑定「当前 Windows 用户」，
所以**以你本人身份运行的程序可以解出**——不需要管理员权限，不需要装插件，不需要关浏览器。
本工具双击运行、跑在你自己的账户下，天然满足这个条件，这也是这条路可行的原因。

> 具体的加密格式与解密步骤不在这里展开：那属于浏览器自身的安全机制细节，与本工具的使用
> 无关，写出来对读者也没有帮助。只需记住结论：**旧版浏览器可读，新版 Chrome 不可读。**

新版 Chrome 起用了更强的本地加密，普通用户权限**根本解不开**——这是 Chrome 的安全设计，
**不要试图提权硬解**。本模块遇到这种情况会**主动放弃**这条路径，自动改走路径二。

实现要点（`cookies.py`）：

1. **只读**：以 `mode=ro` 打开 cookie 库，绝不写入；浏览器正运行持锁时，退回
   `shutil.copy2`（失败则如实报告"读不到"，不做任何绕锁的危险动作）。
2. **按域+按名筛选**：只取 `scnu.edu.cn` 相关、且属于身份认证白名单的条目
   （`MoodleSession` / `my_client_ticket` / `JSESSIONID` / `cookie_session_id` /
   `machineSerial` / `login_type` / `login_user`）。Matomo 统计（`_pk_*`）、主题偏好
   （`theme_*`）之类一律丢弃——它们与登录无关，混进请求头只会变脏。
3. **如实汇报**：`inspect_profiles()` 对每个 profile 给出「库是否可读 / 是否已登录平台 /
   是否已登录统一身份认证」，`radar.bat import` 打印这份体检表，找不到会话时给出可执行的下一步，
   绝不静默失败。
4. **新版浏览器安全降级**：遇到解不开的新版加密格式时，本模块**主动跳过**并返回 `None`，
   然后由 CLI 自动改走路径二——**不做任何提权或破解尝试**。

**路径二：`radar.bat browser` —— 让浏览器自己交出会话（新版 Chrome 的正解）**

新版 Chrome 的本地加密解不开，但浏览器**自己**知道所有 cookie。只要给它开一个调试端口，
就能通过浏览器官方的调试协议（Chrome DevTools Protocol）把 cookie 要出来——这是浏览器
**主动提供**的能力，不涉及任何解密，也不需要任何权限。
实现见 `cdp.py`，只用标准库（`subprocess` 起进程、`socket` 手写 WebSocket 帧、
`urllib` 做 HTTP 探测）。

流程：

1. `radar.bat browser login` 以 `--user-data-dir=data/browser_profile`（**私有目录**，绝不碰
   你的日常浏览器）起一个**可见**窗口，并在**随机 9333–9359 端口**开调试端口；
2. 你在窗口里登录一次平台（工具**不自动填表**，见下）；
3. 工具**只读地**轮询当前页面的登录态，用与 `session.is_logged_in_html` 同一套铁证判定
   （出现 `login/logout.php`，或 `M.cfg.userid >= 2`）；
4. 一旦登录成功，立刻用 `Network.getAllCookies` 取回 cookie 明文、落盘到 `config.toml`。

关键约束与要点：

- **轮询期间绝不导航（重要）**。这里踩过一次真坑：早期实现每 3 秒调一次会导航的
  `snapshot()`，结果用户正在统一身份认证页面敲账号密码时，页面每 3 秒被刷回 `/my/`，
  表单反复清空、根本没法输入。现在把「纯读取」`_read()` 与「导航」严格分开：
  `wait_for_login()` 只调 `_read()`，任何一次导航都只发生在**启动那一刻**（用户还没开始
  输入时）。`tests/test_cdp.py` 有专门的回归测试钉死这条（`wait_for_login` 调用期间
  `navigate` 必须零次）。
- **Chrome 拒绝对「默认」用户数据目录开远程调试**（会报
  "DevTools remote debugging requires a non-default data directory"）——用私有目录正好规避，
  也顺带满足"绝不碰用户日常浏览器"的原则。
- **必须附着到 page 目标**：浏览器级 WebSocket 目标不支持 `Network.*` 域，要从 `/json/list`
  里挑 `type == "page"` 的那个；私有目录可能残留多个标签页，所以**优先挑网址里含平台主机
  的那个**，连错时也只在启动那一刻纠正一次。
- **登录页（`AccountService/user/login.html`）带条件显示的验证码**（`rancode`，默认
  `display:none`，多次失败后才出现），所以工具**不去自动填表**——登录动作交给用户，
  我们只负责把登录后的会话收好（这也顺带避开了把账号密码交给程序的安全问题）。
- 私有目录里的登录态是**持久的**：登录一次之后，`radar.bat import` / `radar.bat browser probe`
  每次都能从该目录读回会话，无需再登录。

**两条路的关系**：`radar.bat import` 先走路径一；当路径一拿不到会话（新版 Chrome 的 `v20`
加密，或 cookie 库被独占）时，**自动改走路径二**并提示用户先运行一次 `radar.bat browser login`。
也可用 `radar.bat import --cdp` 强制走路径二。

两条路径都只解决「拿到会话」，**不改变**"最后一公里"未打通的结论：自动续期仍然不可用，
会话过期后的动作依旧是把浏览器登录态重新取一次——只是从"手抄 30 秒"变成"跑一条命令 10 秒"。

### 4.5 让"重新登录"这件事基本消失：浏览器静默续期

第 4.3 / 4.4 节说的都是"怎么把会话取回来"。但用户真正想要的是**根本不用管**。
2026-10-10 补上了这一步，思路只有一句话：

> **`requests` 走不通登录链路，但真实浏览器能走通——那就让浏览器替我们去走。**

网关认浏览器：只要私有配置目录里的 SSO 会话还活着，让浏览器访问一次平台，
网关就会**静默**重新登录（SSO 免密），用户一个字都不用输。`relogin.refresh_via_browser`
做的就是这样一趟：无头打开私有目录 → 导航 `/my/` → 判定登录态 → 取回新会话写回 config。

它在轮询里挂了两处：

| 时机 | 行为 |
|---|---|
| **临期前**（每 `browser_refresh_hours`，默认 4 小时） | 主动静默续一次，让会话根本不过期。**但走令牌通路时整个跳过**——数据已不依赖会话，会话只剩截图用途，而 SSO 已死时这一步要等浏览器调试端口超时（实测 61 秒），不值得拖累每轮轮询 |
| **过期后**（轮询撞上 `SessionExpired`） | 作为最后一道补救，救回来就继续，不打扰用户 |

主动续期还有一层意义：**定期让浏览器走一遍登录，本身就让 SSO 会话保持活跃**——
这把"每天都要重新登录"变成了"基本不用管"。

三条工程约束，都是踩出来的：

1. **限流记录的是"上次尝试时间"，不是"上次成功时间"。** 一开始只记成功时间，
   结果 SSO 已死时续期必然失败、成功时间永远不更新，于是**每轮都想再起一次浏览器**。
2. **`BrowserSession.start()` 失败时必须先 `stop()` 再抛异常。** 否则半启动的 Chrome
   会一直占着私有 profile，导致**之后每一次**启动都失败（报"profile 被占用"）——
   而且看起来像环境问题，很难联想到是上一次留下的残骸。
3. **测试里默认把续期替成"永远失败"。** 否则凡是走到"会话过期"分支的用例都会真的去起
   一次 Chrome，单个测试从 0.2 秒变成 30 秒。
4. **走令牌通路时直接跳过主动续期（2026-10-14）。** 令牌让数据完全不依赖会话之后，
   会话只剩"作业页截图"一个用途；而 SSO 已死时这一步要**等浏览器调试端口超时
   （实测 61 秒）**才回来。清单打开时会现场刷一轮，用户能直接感觉到慢——
   实测一轮轮询因此从 30 秒变成 500 秒。所以 `_maybe_proactive_browser_refresh`
   在有令牌时直接 return。

### 4.6 令牌通路：把"会话"这一环整个拆掉

4.1~4.5 五节都在跟同一件事较劲：**怎么让程序手里有一个能用的 `MoodleSession`**。
令牌通路的思路是——**根本不需要它**。

平台自己提供 web service：用户在 `/user/managetoken.php` 可以**自助创建**一枚长期令牌
（`ws_token`，可随时吊销），之后 `POST /webservice/rest/server.php` 用 `wsfunction`
直接拿结构化 JSON。实测（2026-10-10，该校服务开放 833 个函数）能覆盖雷达的整个数据面：

| 需要什么 | 用哪个函数 |
|---|---|
| 账号 / `userid` | `core_webservice_get_site_info` |
| 课程列表 | `core_enrol_get_users_courses` |
| 作业名 / 截止时间 / `cmid` | `mod_assign_get_assignments` |
| **老师附件** | 同上返回的 `introattachments`（`fileurl` 挂 `?token=` 即可下载） |
| **我的提交状态** | `mod_assign_get_submission_status`（学生可用） |
| **我的评分** | `gradereport_user_get_grade_items`（**必须传 userid**，否则被判成"查看其他人的成绩"） |

**取不到的**：批量版 `mod_assign_get_submissions` 需要 `mod/assign:grade`（教师权限），
学生调用返回 "No access rights in module context"。整页截图也只能靠真实浏览器。

一次轮询只有 `1（课程）+ 1（作业）+ N（提交状态，N = 复查队列长度）`个请求，全是小 JSON；
HTML 通路要抓十几个页面。而且**它完全不碰 cookie**，会话死活与数据新鲜度就此脱钩。

三个值得记下来的坑：

1. **`Moodle mobile web service` 是被裁剪过的服务。** 建令牌时下拉框里名字最像的那个，
   标准函数**全被校方挡掉**（`accessexception`）。要选学校自建的 **`学校自建的服务`**
   （校内 App 在用，`Attendance` / `ai_box` / `sjj` 同为学生自建、可作备选）。
   诊断口诀：**`accessexception` = 函数存在但不在这个服务里；`invalidrecord` = 函数压根
   不存在。** 拿这两个错误码当探针，可以判断一个函数名是否有效，不需要有权限调用它。
2. **"本学期"不能只按课名过滤。** HTML 通路靠"我的课程"侧边栏的**教务分组**，API 没有分组；
   只匹配课名里的学期后缀会得到 4 门，**漏掉 2 门正在上的课**（`编译原理与方法`、
   `计算机网络基础` 的课名里没有后缀）。改用课程自己的起止时间
   （`startdate <= now <= enddate`）得到 7 门——多出一门没被侧边栏收录的。**宁可多留一门，
   也不能漏掉正在上的课**，这与雷达"宁可多提醒，不能漏交"的取舍一致。
3. **批量拿到的截止时间不能顺手写进 `update_detail`。** 那个方法会把 `last_checked` 推到当下，
   于是那条作业被踢出复查队列最长 24 小时，**提交状态反而变旧**。所以单加了一个
   `store.update_due()`：只写 `due_ts` / `due_text`，不碰 `submitted`、不动 `last_checked`。
   两条队列（截止比对 / 提交状态复查）各走各的，互不顶掉对方的进度。

**回退是保底。** `ws_token` 没配、被吊销、服务被裁剪、网络不通，`_poll_body` 都会自动退回
原来的 HTML 路径——旧路一条都没删。`WsUnavailable` / `WsError` 之外的异常故意不吞：
那多半是我们自己的 bug，该露出来。

## 5. 怎么知道"有新作业"：快照对比法
平台没有提供"有新作业就推送给某个程序"的通道，所以程序采用最朴素也最可靠的办法：
**定时巡逻 + 台账对比**。

### 5.1 台账（SQLite 数据库）

`data/state.db` 是一个 SQLite 文件——可以理解为**一本单机台账**，不需要安装任何
数据库软件，就一个文件。里面主要是一张"作业表"：

| cmid（作业编号） | 课程 | 作业名 | 截止时间 | 是否已交 | 首次发现时间 | … |
|---|---|---|---|---|---|---|

关键设计是 **cmid 作主键**：平台给每个作业分配一个全站唯一的编号（比如 123456），
它就是作业的"身份证号"。每轮巡逻发现的每个作业，程序都拿编号去台账里查——

- **查不到** → 新作业！记入台账，发"新作业"通知；
- **查到了** → 对比截止时间等字段，变了就发"变更"通知，没变就静默；
- **台账里有、这轮没看到** → 不管它（可能老师删除或课程归档），不删记录。

因为只认编号，**巡逻跑多少遍、程序重启多少次，结果都一致**（这叫"幂等"），
不会出现"重启后把老作业当成新的再轰炸一遍"的事故。首次运行时程序会做一次
"基线巡逻"——把当时已存在的所有作业静默记为已知，只建台账、不发通知，避免
第一天就把几十条历史作业全部弹给你。

**另有独立的「评分表」（2026-10-14 加）。** 成绩册和作业不是一回事，所以没往作业表里
塞列，而是单开一张：

| item_id（评分项编号） | 课程 | cmid | 作业名 | 分数 | 满分 | 评分于 | … |
|---|---|---|---|---|---|---|---|

- **用独立表而不是给作业表加列**：已有的 `state.db` 不用迁移（`CREATE TABLE IF NOT EXISTS`
  就够），而且成绩册里还有**课程总分**这种不对应任何作业的项（`cmid` 为空），硬塞进作业表
  反而别扭。
- `cmid` 非空时能和作业表**直接对上**（平台给评分项也带 `cmid`），所以"这次评分对应哪份作业"
  不需要猜。
- **按 `item_id` 幂等**：老师改分、补评分都能跟上，不会重复记账。
- 只存不用在通知上——目前它只喂终端清单的"📊 评分"区。

### 5.2 提醒的节奏

台账里还有一张"提醒发放记录"表：每个作业在每个提醒档位（默认：截止前 24 小时）
只能提醒一次。程序每轮巡逻会扫描"即将在 24 小时内截止且未确认提交"的作业，
没提醒过的才提醒。老师如果改了截止时间，旧提醒记录作废、按新时间重新排——
这就是"改期也能收到提醒"的实现。

## 6. 一次轮询的完整旅程

把两小时一班的巡逻从头到尾走一遍（数字是真实的请求量级）。**配了令牌走 A，没配（或
令牌失效）自动退回 B**——两条路产出完全一样，只是 A 不碰 cookie、请求也少得多。

### 6.0 两条通路

**A. 令牌通路（默认，见 4.6）**

```
① 定时器到点（120 分钟 ± 10% 随机抖动，抖动是为了避免请求轨迹太规律）
        ↓
② core_enrol_get_users_courses（1 个请求）
   └─ 本学期 7 门课（课名含学期后缀，或起止时间覆盖现在）
        ↓
③ mod_assign_get_assignments（1 个请求，所有课程一次拿完）
   └─ 31 个作业的编号 / 名称 / 截止时间 / 老师附件（introattachments）
        ↓
④ 编号对台账：挑出没见过的（正常日子 = 0 个）
   └─ 有新的 → mod_assign_get_submission_status 查一次提交状态 → 入库
        ↓
⑤ 截止时间比对：**零额外请求**（数据在 ③ 里已经全有）
   └─ 变了 → 发"变更"通知（老师拖堂也能知道）
        ↓
⑥ 提交状态复查（两档节奏，限额 15 个/轮，错峰，见下）
        ↓
⑦ 评分同步：每门课一次 gradereport_user_get_grade_items（7 个请求）→ 写评分表
        ↓
⑧ 扫描提醒 → 附件归档（已存在的直接跳过，正常情况零请求）
   → 全部写台账 + 一条巡逻日志（data/radar.log），本轮结束
```

约 20 个请求、**30 秒左右**，**全程不碰 cookie**——所以会话过期也照常跑。

**B. HTML 通路（保底）**

没配令牌、令牌被吊销、服务被裁剪、网络不通时会自动走到这里：

```
② 访问"我的课程"页（第 1 个请求）
   ├─ 页面被弹到登录页？→ 会话过期，走第 4 节的三级防线，本轮结束
   └─ 正常 → 解析侧边栏，得到本学期 7 门课
        ↓
③ 逐门课访问课程页（7 个请求，每个间隔 1.5 秒）
   └─ 每门课页面里筛出"作业"类型的条目 → 得到 28 个作业的编号、名称、链接
        ↓
④ 编号对台账：28 个里挑出没见过的（正常日子 = 0 个）
   └─ 有新的 → 逐个访问作业详情页，解析截止时间和提交状态
        ↓
⑤ 复查队（两档节奏，限额 15 个/轮，错峰）
   └─ 重看详情 → 截止时间变了 → 发"变更"通知
   └─ 提交状态变了 → 更新台账（补交的作业会从"未提交"移到"已提交"）
        ↓
⑥⑦⑧ 与 A 相同（提醒 / 附件归档 / 写台账 + 巡逻日志）
```

一整轮约 10~35 个请求、耗时不到一分钟；一天 12 轮，对学校服务器来说
相当于你本人每天多刷了几十次页面，负载可以忽略。

> **每轮都会记下自己用了多久（2026-10-14）。** `_finish` 用 `time.monotonic()` 量**端到端**
> 耗时——包含会话续期、浏览器静默续期这些**不在轮询主体里**的等待，因为那才是用户真正
> 等掉的时间。写两处：① `PollSummary.duration` 进 `describe()`，于是 `poll_log.detail`
> 里天然留了历史，**不用给表加列**；② `meta.last_poll_duration` + `meta.last_poll_path`，
> 供只读缓存的清单标题行显示（`📋 作业清单 · 数据更新于 …（用时 27.2 秒 · 令牌通路）`）。
> 用 monotonic 而不是 wall clock：系统校时不会把耗时算成负数。**失败轮询同样记耗时**
> ——61 秒那种多半是卡在浏览器续期的调试端口超时（见 §4.5）。

> **刷新与读取是两件事（2026-10-14 定调）。** 刷新（produce）贵——网络密集、5~40 秒；
> 读取（consume）便宜——只读台账、零请求。早期版本把两者压在 `radar.bat list` 里
> （打开就现场刷一轮），于是每次打开都要等半分钟。现在职责切开：
> **刷新**由常驻进程负责（`radar.bat run` 或 `radar.bat loop`，见 8.4），**读取**永远只读
> 缓存。触发源因此可以有三个而不互相干扰——常驻循环、一键启动器、用户手动——
> 关键前提是**刷新增密 + 台账幂等**，所以"谁触发"只是部署选择，不是代码改动。
> 这条也解释了为什么 `radar.bat loop` 不与 `run` 并排抢：它们共用同一把实例锁。

> **两档复查节奏（A 和 B 共用）**：
>
> * **临近截止（±12 小时）且尚未提交的** → 每 **20 分钟**复查一次。学生多半在这时交
>   作业、交完立刻打开清单，状态必须新鲜；
> * **其余的**（未截止 / 截止未知 / 已截止但没交）→ 每 **24 小时**复查一次。


> **为什么复查队里必须有"已截止但没交"的作业？** 这里踩过一次真坑（2026-10-08）：
> 早期版本用 `due_ts >= now` 把已截止作业排除在复查之外，结果**提交状态会在截止
> 那一刻被永久冻结**。学生卡在截止前一小时交作业，雷达截止前最后一次抓取记下
> "未提交"，截止一过就再没人去更新它——清单里于是永远显示"未提交"，把人吓得
> 以为作业白交了。卡点交作业恰恰是最常见的情形，所以这条队列不能省。

### 6.1 附件归档：只收"老师给的"

平台的作业详情页里，`pluginfile.php` 链接其实有**两种**：

| 链接特征 | 是什么 | 归档吗 |
|---|---|---|
| `mod_assign/introattachment/…` | 老师随作业发布的资料（讲义、指导书、素材） | ✅ 收 |
| `mod_resource/content/…` | 课程文件区里被引用到的资料 | ✅ 收 |
| `assignsubmission_file/submission_files/…` | **你自己交上去的作业** | ❌ 不收 |

这个区分很关键——不排除后者，归档目录会被自己的作业文件塞满，反而找不到老师的资料。
实现上就是一句话：链接里含 `assignsubmission_file` 就跳过（`moodle.parse_attachments`）。

落到磁盘的路径是 `<homework_dir>/<科目文件夹>/<作业>/<文件>`：**一个科目一个文件夹**，
作业再分一层，避免同一门课不同作业出现同名文件互相覆盖。

**科目文件夹不是课名的机械转换，而是一次查表。** 学生往往早就按科目建好了自己的
文件夹（`D:/我的作业/web`、`.../db`、`.../编译`…），而这些名字和平台的课名
（`Web 应用开发(26-27 上学期)`）八竿子打不着。所以 `config.toml` 里有一张
`[course_dirs]` 映射表，查表顺序是：

1. 完整课名（`Web 应用开发(26-27 上学期)`）；
2. **去掉学期后缀的裸课名**（`Web 应用开发`）——映射表的键按裸课名写，
   这样下学期课名变成 `(27-28上学期)` 也不用改配置；
3. 都没命中 → 退回裸课名，在归档目录下新建一个同名文件夹，**并在输出里明确提醒**。

第 3 步的提醒是刻意的：映射配错了（比如把 `web` 敲成 `wben`）会静悄悄散落一地，
学生根本发现不了；所以宁可啰嗦一句，也不让错配无声发生。

两个工程细节：

- **幂等**：目标文件已存在就跳过。所以归档既可以手动 `radar.bat attach` 全量扫一遍，
  也可以挂在每轮轮询上——第二次之后零成本，不会因为"怕重复下载"而不敢重跑。
- **不认登录页**：会话过期时平台会把 `pluginfile` 请求重定向到登录页，返回的是
  HTML 而不是文件。这种一律判为失败并记日志，**绝不把 HTML 当成附件存下来**
  （否则磁盘上会出现一堆内容其实是登录页的"PDF"）。

### 6.2 整页截图：给归档留一份"原件复印件"

归档的本质是"程序替你读网页"。读漏了、读错了，学生打开文件夹是**看不出来**的——
附件少了，他可能以为是老师没发。所以每份作业额外留一张布置页面的**整页截图**
（`_作业页截图.png`），附件与截图并排放着，一眼就能核对。

技术上只有一个要点：**截图必须靠真实浏览器渲染**。`requests` 拿到的是没有版面的 HTML，
排版、图片、表格全是散的，截出来没有意义。所以这条路走 CDP（第 4.4 节那套私有配置目录
的浏览器），用 `Page.captureScreenshot` + `captureBeyondViewport` 按**内容实际高度**出图，
而不是只截视口那一屏。

由此带来三条约束，都是刻意的：

1. **需要先 `radar.bat browser login` 一次。** 没登录时渲染出来的是登录页——那种截图毫无价值。
   所以开跑前先预检登录态，不通过就**只提示、不报错**：附件归档照常完成，不能因为
   "截不了图"就让整个命令看起来失败。
2. **每一页都重新确认登录态。** 会话可能在半路失效；发现掉了立刻停止，
   **绝不往归档里塞一沓登录页冒充截图**（这比不截图更糟——它会让人以为归档是完整的）。
3. **没有附件的作业也要截。** 只有这样学生才能确认"这份作业确实没有附件"，
   而不是"程序漏下了"。所以截图清单来自**所有作业**，不是只有带附件的那批。

顺带一个工程上的巧合：截图清单恰好可以复用附件扫描时的那次遍历——`collect()` 本来就
逐份访问作业页，加一个 `on_assignment` 回调就顺手攒出了清单，不必为此多跑一遍请求。

## 7. 通知是怎么弹出来的

通知走的是一条**异步传送带**：轮询水手发现事情后，把"通知任务"丢进一个队列
（可以想成一个待传送的托盘）就继续巡逻去了；另一个专职水手从队列里取任务、
依次弹 Windows 系统通知。这样即使通知失败（比如 Windows 通知服务抽风），
也绝不会卡住巡逻本身。

通知的三个通道：

- **Windows 系统通知**（默认开）：用的是 win11toast 库。它支持"点击回调"——
  通知里埋了作业的网址，你一点击，程序就调起浏览器直达该作业页。这就是
  "点一下就跳到作业"的实现；
- **ntfy 手机推送**（可选）：ntfy 是一个免费的"往指定频道发消息"的公共服务，
  程序往你订阅的私密频道发一条带链接的消息，手机 App 收到后点开同样直达；
- **Server酱**（可选）：通过微信服务号推送，原理类似。

托盘图标也是状态灯：绿 = 会话正常，红 = 登录过期，灰 = 还没检查过。

## 8. 三个用户入口的原理

同一个台账，三个橱窗：

### 8.1 全局热键 Ctrl+Alt+R（由配套启动器注册）

本项目之外还有一个配套的常驻启动器，它用 `keyboard` 库在系统层面挂了一个
**全局键盘钩子**——无论你正在用哪个软件，按下它都能收到。收到后它**新开一个终端
窗口打印当前作业清单**（看完回车关闭）。

2026-10-14 改了两处，起因是"每次打开都要等半分钟"：

1. **键位 `Ctrl+Alt+A` → `Ctrl+Alt+R`。** `A` 撞 QQ 的截图快捷键（微信占 `Alt+A`），
   而 `R` 是启动器那边腾出来的空键。换键通过启动器侧的环境变量配置，本工具不感知。
2. **热键不再负责"拉起常驻"。** 以前按一下会顺带起 `radar.bat run`（托盘 + 面板 + 轮询），
   于是热键既要"让人看见"，又要"保证有人在后台刷"。现在后台刷新交给
   `radar.bat loop`（见 8.4 节），由启动器统一拉起；
   热键只做一件事：**弹出清单**。责任单一只会让链路可预测。

⚠ **弹窗口必须用 `python.exe` + `CREATE_NEW_CONSOLE`**，不能用 pythonw——
它是 GUI 子系统，不给它一个自己的控制台就什么都看不见。

防重复的机关叫**单实例守卫**：常驻实例会在本机 8731 端口开面板服务（`run`），
或在 `data/radar.lock` 上持文件锁（`run` / `loop` 都持）。新实例启动前先试探——
敲得通/抢不到锁说明已经有自己在跑了，于是只弹清单、自己退出。所以热键按多少次
都不会出现两个轮询程序同时跑。这把锁也顺带让 `run` 与 `loop` **天然互斥**。

### 8.2 终端命令 radar.bat list

`list` 命令读台账、按规则排版打印：未交的在前（已截止 → 按截止时间升序 →
未知截止），已交的在后（只显示最近 3 个）。颜色是终端的 ANSI 转义码——
本质是打印时夹带的特殊字符，终端见到就换颜色，复制成纯文本时自动消失。

**2026-10-14 起默认只读缓存、零请求**（实测 1.6 秒，改之前要 25~40 秒）。
后台循环每轮把结果写进台账，`list` 只读那份快照；要现场刷新才加 `--refresh`。
数据比两个轮询周期还旧时显眼提示「下面是过期数据」并告诉用户 `--refresh`——
所以"缓存"不等于"蒙在鼓里"。

### 8.3 本地面板 http://127.0.0.1:8731

程序内置了一个**只有你的电脑能访问**的迷你网站（Python 标准库的 http.server，
十几行就够，因为它只有一个页面）。页面是一份内嵌的 HTML + 原生 JavaScript，
每 60 秒向程序要一次最新数据（JSON 格式）自己重画。没有引入任何网页框架——
对单页面来说，框架是负担而不是帮助。

### 8.4 无头刷新循环 radar.bat loop

`radar.bat loop` = **只轮询**：不托盘、不面板、不弹窗。它存在的唯一目的是
"保证有人在后台定时刷新，并把结果写进台账"，好让 8.1 / 8.2 / 8.3 三个入口都拿到
**零等待**的快照。配套的启动脚本已经接上（`RADAR_LOOP=0` 可关）。

三条要点：

1. **`loop` 与 `run` 共用 `data/radar.lock`**（8.1 的单实例守卫同一把锁）。
   谁先起谁跑，另一个探测到"已有人在跑"就安静退出 0。这把锁是这个项目最便宜的
   正确性保证——历史教训是两个实例跑了三个多小时，双倍轮询、双倍通知、并发写同一个
   SQLite。
2. **托盘与面板仍是 `run` 的活**，`loop` 刻意不碰：一键启动器自带窗口和服务，
   再弹托盘只会添乱。
3. **没有控制台也不崩**：pythonw 拉起时 `sys.stdout` 是 `None`，`print` 会直接抛。
   `loop` 内部的输出走一个吞异常的 `say()`。

## 11. 关键设计决策及理由

| 决策 | 为什么 |
|---|---|
| **定时轮询**，而不是"网站推送给我" | 平台没有对外推送通道；2 小时一班对"作业"这种以天为单位的事物完全够用 |
| **cookie 方案**，而不是自动输账号密码 | 不碰密码就少一类风险；SSO 登录页虽无验证码，但模拟登录属于学校明令敏感区，性价比不高 |
| **只读**，绝不模拟点击"提交" | 工具的边界：它替你看，不替你做 |
| **归档附赠整页截图** | 附件少了/读错了，从文件夹里看不出来；一张布置页整页图就是"原件复印件"（见 §6.2） |
| **令牌优先、HTML 保底** | 会话约 10~12 小时就死，死了清单就停在旧数据上。令牌走 REST 接口不碰 cookie，数据新鲜度与会话死活脱钩；但旧路一条不删，令牌不可用时自动回退（见 §4.6） |
| **附件只归档"老师给的"** | 作业页上 `assignsubmission_file` 是你自己的作业，收进来只会把老师的资料淹没（见 §6.1） |
| **归档幂等（存在即跳过）** | 否则"怕重复下载"会让人不敢重跑；幂等之后挂在每轮轮询上也是零成本 |
| **放弃浏览器扩展方案** | 浏览器扩展在新安全规则下拿不到跨站 cookie（等于没法替你登录），且要求浏览器常开 |
| **单文件 SQLite**，而不是联网数据库 | 个人工具，零运维；备份 = 复制一个文件 |
| **请求限速 + 随机抖动 + 限流退避** | 对学校服务器礼貌，也降低被识别为异常流量的概率 |
| **单实例靠文件锁，不靠端口探测** | 端口探测是竞态的：两个进程可能同时发现"还没人监听"而双双启动（2026-10-09 实测两个实例同一秒启动、一起跑了三小时，双倍轮询双倍通知）。文件锁由 OS 在进程退出时自动释放，既原子又不留死锁文件 |
| **标准库优先，依赖只 6 个** | 学生机器环境多变，依赖越少越皮实 |
| **自动化测试 215 项** | 解析器最怕"网站改版悄悄坏了没人知道"——用离线样例页把解析逻辑钉死 |

## 12. 安全设计

- **凭证最小知情**：程序只保存 cookie（临时凭证），永不保存账号密码；配置文件
  `config.toml` 是唯一的凭证存放点，权限限定在你自己的用户目录；
- **面板仅本机**：面板服务绑定 127.0.0.1（回环地址），同一个宿舍网的其他设备无法访问；
- **只读边界**：代码里不存在任何向平台提交数据的路径（无选课、无提交、无留言）；
- **数据本地化**：作业记录、日志全部在本机，不经过任何第三方服务器
  （唯一的例外是可选的 ntfy 推送——消息内容经 ntfy.sh 中转，因此频道名必须足够随机）；
- **附件归档不外传**：`radar.bat attach` 只把老师发布的资料下载到本机 `homework/`，
  不上传、不分享；该目录已在 `.gitignore` 里（课程资料属他人版权内容，不进版本库）；
  文件名经 `safe_name` 消毒（抹掉路径分隔符、`..`、Windows 非法字符），
  附件**不可能**写到归档目录之外；会话过期时 `pluginfile` 返回的登录页 HTML 会被
  识别并拒绝，不会被当成附件存盘；
- **浏览器 cookie 的读取边界**：`radar.bat import` 只读取（`mode=ro`）Chrome/Edge 的 cookie 库，
  **从不写入、不修改**用户的浏览器数据；解密依赖 Windows DPAPI 的「当前用户」密钥，
  因此**只有你本人在本机才能解开**，程序也不需要管理员权限；提取内容限定为 `scnu.edu.cn`
  域下身份认证相关的少数条目，其余（含其他网站的任何 cookie）不读取、不落盘、不外传；
  新版 Chrome 的 `v20`（App-Bound）cookie 则**刻意不解**（那是系统级 DPAPI，需要提权）；
- **`radar.bat browser` 的调试端口**：调试协议只在**本机回环地址 `127.0.0.1`** 的随机端口
  （9333–9359）上监听，**不对外开放**；浏览器实例以 `--user-data-dir=data/browser_profile/`
  指向私有目录，与用户日常浏览器的 Profile 完全隔离，既不读取也不修改日常浏览器数据，
  也不会关闭用户正在用的窗口；登录窗口关闭后调试端口随之消失；
- **泄露预案**：cookie 泄露 = 别人可冒充你浏览（不能改密码、不能提交作业）；
  去统一身份认证改密码即可使所有旧 cookie 全部作废。

## 13. 已知限制与权衡

1. **SSO 自动续期依赖 SSO 会话存活**：续期（重走登录链路）与保活（给 SSO 会话续命）
   都以你录入的 SSO cookie 为起点；若 SSO 会话被服务端判死（改密码、超长不活跃等），
   工具会提前弹"SSO 会话已失效"预警，此时需人工重新复制一次。若日后仍嫌频繁，
   可升级为本地保存账号密码的全自动登录（需要用户明确授权）。
   补充记录（2026-10-09 起多次复测）：平台的登录入口与网关行为在校方侧几经调整，
   用纯 HTTP 客户端复现整条登录链路始终走不通。
   **但更根本的原因在下面**：校方在登录环节部署了专门的反自动化措施（人机校验 +
   提交前的密码加密），**刻意对抗它们不是本项目的目标**——既不稳定，也不合适。
   所以结论比原来更硬：**会话过期后请用 `radar.bat browser login` 重新取一次**，
   不要指望自动续期。CLI 的失败提示已改成直接告诉用户敲这条命令，
   而不是让人去"检查 sso_cookie"。
   正解是绕开这条路：**走 4.6 的令牌通路**。
2. **只监控"作业"类型**：测验（quiz）、问卷等模块不在监控范围——这是当初的需求边界，
   扩展只需在解析器加一个类型。
3. **提交状态的"未提交"有两种来源**：平台的作业状态表被主题精简，**没交**的作业页面上
   往往没有明确字样，解析结果只能是"未知"；而"未知"在清单里和"确认未交"一样按未提交展示。
   所以看到"未提交"先别慌——点进去看作业状态那一行（"已提交请评分"才是铁证）。
   提醒逻辑按"未确认提交=会提醒"处理，宁可多提醒一次也不漏。
   另注：**提交状态是有复查延迟的**——临近截止（±12 小时）的作业每 20 分钟复查一次，
   其余每 24 小时一次。刚交完就打开清单，最坏情况下要等一个复查周期才会变绿。
4. **部分截止时间靠"剩余时间"反推**：个别页面没有绝对日期时，用"仅剩 X 天"折算，
   误差 ≤ 轮询间隔（2 小时）。
5. **网页改版会使解析失效**：这是所有抓取工具的宿命。对策是 215 项离线测试 +
   `check --save-html` 一键导出脱敏页面供排查。
6. **`radar.bat import` 读不到正在运行的 Edge**：Edge 运行时会以独占方式锁住 cookie 库
   （SQLite 在线备份与直接复制都会撞 `WinError 32`），此时改用 Chrome 或先退出 Edge。
   Chrome 不受影响——它同样持锁，但锁的粒度允许只读打开。
7. **新版 Chrome 的 `v20` cookie 直读不了**：Chrome 127 起启用 App-Bound Encryption，
   新 cookie 密文前缀是 `v20`，密钥由**系统级** DPAPI 保护，普通权限无解（**不建议提权硬解**）。
   对策是走 CDP（路径二）：`radar.bat import` 检测到这种情况会自动改走 CDP，并提示先
   `radar.bat browser login` 登录一次；那一次的会话会留在私有目录里，之后一直可读。
8. **CDP 路线需要 Chrome 或 Edge 已安装**：找不到浏览器时会明确提示，可 `RADAR_BROWSER=<路径>`
   指定；这条路线不适用于完全没有图形浏览器的最小化环境。
9. **`radar.bat browser` 不自动登录**：登录页带条件显示的验证码（`rancode`），且把账号密码
   交给程序本身也不合适——所以只做"打开窗口让你登录一次"，不做自动填表。

## 14. 小词典

| 术语 | 通俗解释 |
|---|---|
| cookie | 登录后网站发给浏览器的一段暗号，之后每次访问随身携带以证明身份 |
| 会话（session） | 你从登录到登出之间的那段"已验证身份"的状态 |
| SSO（统一身份认证） | 学校的"一次登录、全校通行"系统，sso.scnu.edu.cn |
| OAuth 授权码 | 一个系统借用另一个系统的身份时的标准"介绍信"流程 |
| 轮询 | 每隔固定时间去问一遍"有新东西吗"，与"推送"相对 |
| 爬虫 / 抓取 | 用程序代替浏览器读取网页内容 |
| HTML / 选择器 | 网页的源文本格式 / 在其中精准定位某类元素的规则 |
| SQLite | 存在一个文件里的轻量数据库，无需安装数据库软件 |
| 端口 | 一台电脑上区分不同网络服务的门牌号（本工具用 8731） |
| 守护进程 / 常驻 | 在后台长期运行、不显示窗口的程序 |
| 托盘 | 屏幕右下角的小图标区 |
| venv（虚拟环境） | 为单个项目隔离安装的 Python 运行环境，避免项目之间互相污染 |
| 线程 | 同一程序内并行工作的多个"分身" |
| 幂等 | 同一操作重复执行多次，结果与执行一次相同 |
| DPAPI | Windows 自带的"加密保险箱"，按用户封装密钥；同用户即可开箱，无需管理员 |
| App-Bound Encryption（`v20`） | Chrome 127+ 的 cookie 新加密：密钥改由**系统级** DPAPI 保护，普通权限解不开（安全设计） |
| CDP（Chrome DevTools Protocol） | 浏览器对外的调试接口；本工具用它的"列出所有 cookie"命令让浏览器自己交出明文，绕开加密 |
| 私有配置目录 | 本工具自己的浏览器数据目录（`data/browser_profile/`），与你的日常浏览器完全隔离 |
